# LLM 대화 발전 구현

최신 실제 엔진·음성·중단 검증은 [실제 검증 기록](live-verification-2026-09-26.md)에 있다.
모델에 제공하는 근거 ID는 턴별 s1/s2로 단축하고, 검증·진단에는 원래 출처 ID를 사용한다.
source_ids 생성 계약은 RAG의 기본 동작이다. dialogue나 natural_grounding을 꺼도 유지되며, natural_grounding은 검증 후 어미 변환만 제어한다.

2026-09-26. 앞서 제안한 9개 발전 방향을 기존 Python 제어 흐름에 연결했다.
모델 가중치를 바꾸는 학습과 실제 음성·방송 수용은 별도 단계다.
공개 채팅 시간 제한·사실 질문 우선 분류·생성 샘플링 설정의 추가 보강은 [생방송 LLM 문서](live-llm-readiness.md)를 참고한다.
기존 RAG의 승인·권한·삭제 검증과 `generate(messages)` / `aclose()` 계약을 유지한다.

## 실행

```powershell
# 외부 엔진 없이 처리 흐름 확인
python -m uv run --locked python -m virtual_ai --backend mock --local-only --dialogue --once "안녕"
# 실행 중인 로컬 LLM을 사용하는 텍스트 대화: 자신의 설정 사용
python -m uv run --locked python -m virtual_ai --config configs/app.yaml --local-only --dialogue
```

`--dialogue` 또는 YAML의 `dialogue.enabled: true`로 활성화한다.
기존 실행과 비교할 수 있도록 기본값은 false다. 이 플래그는 TTS·RAG·기억 저장을 켜지 않는다.
RAG 활성화·문서 등록·기억 동의는 [RAG 운영 문서](llm-rag-plan.md)를 따른다.
`/status`의 dialogue 필드는 마지막 처리 유형·질문 수·묶인 시청자 수를 보여준다.

```yaml
dialogue:
  enabled: true
  style: polite                 # 근거 문장의 polite / casual 어미
  natural_grounding: true
  contextual_memory: false      # 승인된 기억을 관련 잡담에서 먼저 언급하는 선택 기능
  memory_cooldown_seconds: 600
  reaction_window_seconds: 2
  reaction_ttl_seconds: 6
  answered_cooldown_seconds: 20
  followup_every: 4
  generation_timeout_seconds: 10
  public_response_ttl_seconds: 20
```

## 제안별 적용 결과

| 발전 방향 | 적용 동작 | 검증·제한 |
| --- | --- | --- |
| 자연스러운 근거 답변 | 모델은 `source_ids`만 선택하고 프로그램이 전체 근거를 검증해 한국어 어미를 변환한다. 사용자 기억은 사실 단정 대신 자기 보고로 표현한다. | 숫자·부정·조건·예외 보존. 자유로운 요약의 의미적 정확성을 입증하는 기능은 아니다. |
| 여러 턴의 흐름 | 시청자별 주제, 후속 질문의 지시 대상, 최대 3개 질문, 최근 답변을 관리한다. 맥락 없는 “그럼 그거는?”에는 확인 질문을 한다. | 최근 맥락은 TTL/LRU로 제한. 한국어 규칙 기반이며 복잡한 생략·다중 주제는 모델 평가가 필요하다. |
| 캐릭터 행동 | `character.yaml`의 aliases와 situation_rules를 프롬프트에 반영한다. 인사·반응은 한 문장, 정확히 반복한 인사·반응은 다른 표현으로 바꾼다. | 질문 허용 주기는 프롬프트 지침이다. 모든 표현의 반복/의미 유사성을 강제 판별하지 않는다. |
| 말할 타이밍 | 다른 사람에게 보낸 @멘션, 오래된 감탄, 최근 답한 동일 질문을 건너뛴다. 2초 이내 같은 플랫폼의 순수 웃음·감탄만 묶는다. | 개인 선호·질문·플랫폼 간 정보는 묶지 않는다. 원래 게시 시각도 확인하며 기존 큐 공정성/중복 억제를 유지한다. |
| 맥락에 맞는 기억 | contextual_memory를 켜면 현재 주제와 맞는 승인 기억만 보탠다. 실제 출력에 사용한 기억마다 쿨다운을 적용한다. | 기존 저장·조회·공개 권한 필요. 요청에 의한 명시적 기억 조회에는 쿨다운을 적용하지 않는다. |
| 정정·복구 | “아니, 나는 싫어한다고 했어”를 직전 자기 보고와 연결하고 현재 대화에서 바로 수정한다. 모호한 정정은 질문한다. | RAM 정정과 영구 기억은 분리한다. 영구 변경은 동의/후보 검토/이전 기억 대체 승인 필요. |
| 감정·표정 일치 | 실패·속상함·정정은 중립 표정으로 제한하고 일부 부적절한 축하 표현을 교체한다. 계획과 출력 검사 모두 맞을 때만 허용 표정을 쓴다. | 모든 감정을 추론하지 않으며 임의 VTS 명령을 생성하지 않는다. 실제 표정·음성 조화는 직접 확인한다. |
| 지연·토큰 관리 | 정정·확인 질문은 LLM 호출 없이 답한다. 일반 생성은 기존 한 번 호출을 유지한다. 이전 기록부터 줄여 현재 맥락을 우선 보존한다. | 예산을 넘으면 선택 맥락을 제외하고 근거까지 못 담으면 안전한 답으로 축소한다. 검증 전 스트리밍 음성은 도입하지 않는다. |
| 평가·모델 개선 | 합성 다중 턴 평가와 실제 로컬 모델 비교 CLI를 제공한다. 실패 유형, 턴 지연 중앙값/p95, 설정·프롬프트 해시, 수동 평가 칸을 남긴다. | 실제 모델 선택과 학습은 평가 결과로 결정한다. 채팅 자동 학습·가중치 자동 다운로드/교체는 하지 않는다. |

처리 순서는 `큐 선택 → 대화 계획 → 필요한 근거 조회 → 생성 또는 고정 응답 → 근거/출력/표정 검사 → 표시·음성 → 상태 기록`이다.
원본 모델 출력 `raw`, 검사 후 `final`, 음성용 `speech`는 계속 분리한다.
대화 상태는 Viewer(platform, user_id)별이며 다른 시청자의 상태를 프롬프트에 넣지 않는다.

## 정정과 삭제의 구체적인 의미

1. 승인된 “나는 퍼즐 게임을 좋아해”를 조회하면 “퍼즐 게임을 좋아한다고 말씀하셨어요”라고 답한다.
2. 같은 시청자의 “아니, 나는 싫어한다고 했어”는 현재 세션의 자기 보고로 정정한다.
3. 해당 선호를 다시 물으면 정정한 내용을 우선한다. 관련 없는 호칭 질문에 선호 정정을 근거로 사용하지 않는다.
4. 저장 동의와 후보 수집이 켜져 있을 때만 정규화한 정정을 후보로 남긴다. 근거에는 실제 정정 원문을 보존한다.
5. 승인 전 후보는 검색할 수 없다. 운영자가 기존 기억을 대체 승인해야 장기 기억이 바뀐다.
6. `/forget`, `/rag-forget`, 기억/지식 기능 전환, 조회 권한 변경·자료 삭제에 따른 revision 무효화는 해당 대화 상태도 지운다.

후보 추가 자체는 검색 가능한 자료를 바꾸지 않으므로 revision을 올리지 않는다.
후보 승인·삭제·권한 변경은 기존 무효화 규칙을 따른다. 잘못된 답변이 차단된 경우 기록·기억 후보를 추가하지 않는다.

## 평가 실행과 모델 비교

```powershell
python -m uv run --locked pytest tests/test_dialogue.py tests/test_rag.py -q
python -m uv run --locked python -m virtual_ai.dialogue_evaluation --report .local/dialogue-next.json
python -m uv run --locked python -m virtual_ai.rag.evaluation --report .local/rag-next.json
# 서로 별도로 실행 중인 로컬 모델/설정을 같은 합성 대화로 비교
python -m uv run --locked python -m virtual_ai.dialogue_evaluation --live-config configs/model-a.yaml --live-config configs/model-b.yaml --report .local/dialogue-comparison.json
```

예시의 model-a/model-b 파일은 실제 서버 주소에 맞게 준비해야 한다. 자동으로 모델을 바꾸거나 엔진을 시작하지 않는다.
모델 비교의 live-config는 backend=koboldcpp, loopback 서버만 허용한다.
설정 model 이름만으로 실제 로드된 모델을 확인했다고 주장하지 않으며 서버의 모델 파일·양자화·샘플링 설정을 별도로 기록한다.
동일 포트에서 순차 교체한다면 각각 별도 보고서를 만든다. 기존 보고서는 덮어쓰지 않는다.

대화 평가: 12개 시나리오, 24턴. 지식 후속 질문, 조건·예외, 정정, 사용자 격리, 공감, 인사 반복, 응답 선택, 모호한 정정, 감정이 섞인 사실 질문, 일상 대화, 부정 표현, 복수 근거 질문을 검사한다.
기본 모드 `scripted_contract`는 의도적으로 반복/부적절한 답을 주는 가짜 LLM으로 제어 흐름을 확인한다.
`live_text_contract`는 실제 모델 출력에 같은 기계적 검사를 적용한다. 테스트에 맞춘 회귀 세트이며 독립적인 일반화 벤치마크가 아니다.
각 시나리오는 임시 DB를 사용하고 실제 시청자·방송·음성·장기 저장소를 연결하지 않는다.
보고서는 원문을 저장하지 않으며 실패를 route/delivery/generation_error/required_fact/forbidden_claim/repetition/speech_contract로 구분한다.
지연은 검색·생성·검증을 포함한 턴 시간이며 TTS 첫 음성 지연이 아니다. 모델 자동 순위는 매기지 않는다.

실제 비교 시 수동으로 캐릭터 일관성·자연스러움·질문 누락·감정 적절성을 각각 1~5점으로 평가한다.
사람 평가 칸은 기본 null이다. 실패한 가상 질문은 해당 case/turn으로 재현하여 확인한다.
근거 위반/다른 사용자 정보 노출/취소 후 출력이 있다면 평균 자연스러움이 높아도 채택하지 않는다.

## 미세조정 및 스트리밍 도입 조건

- 검색 누락·잘못된 승인 자료·컨텍스트 예산 문제를 모델 학습으로 해결하려 하지 않고 해당 단계를 수정한다.
- 같은 모델에서 프롬프트·예시·표면 어미를 보완한 뒤에도 반복되는 말투/지시 이행 문제가 있는지 실패 사례를 분류한다.
- 학습을 검토할 때는 사용 권리가 확인된 가상/검수 대화만 준비하고 학습·검증·최종 평가 세트를 분리한다. 실제 시청자 기록의 자동 변환은 제공하지 않는다.
- 동일 엔진·양자화·샘플링·문맥 예산으로 기존 모델과 비교하고, 사실성·삭제·취소 회귀를 모두 다시 통과해야 한다. 보고서의 fine_tuning_ready는 자동 true로 바뀌지 않는다.
- 스트리밍은 완결된 검사 단위에서 조건·예외 누락 방지, 취소 후 버퍼 정리, 첫 음성 지연의 실제 개선을 확인한 후 도입한다. 현재는 검증된 전체 답변을 음성에 전달한다.

실제 실행 결과는 [대화 확장 검증 기록](dialogue-validation.md)에 기록한다.
