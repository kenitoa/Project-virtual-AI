# YouTube Live 채팅 입력 — 실제 연결 검증 대기

readiness의 운영 제어 변경부터 YouTube 활성 실행은 기본 일시 정지로 시작한다. `/resume` 전에는
수신 위치만 갱신하고 메시지는 버린다. 재개 시각 이전 게시 메시지는 지연 수신되어도 버린다.
`/stop`은 여전히 수신을 중지하지 않는다. 지속 잠금은 `/pause` 또는 `/panic`을 사용한다.
실제 수신 검증은 대기이며 [운영 제어](operator-controls.md)에 복구 조건을 기록했다.

첫 플랫폼은 YouTube Live입니다. 치지직은 별도 후속 작업으로 남깁니다.
OBS 로컬 녹화가 아직 검증되지 않았으므로 현재는 가짜 HTTP 전송 계층으로만 검증합니다.
실제 인증·채팅 수신·음성·모델·녹화의 종단 간 성공을 뜻하지 않습니다.

## 입력 경계

`YouTubeChat.run(app.submit)`이 일반 텍스트 이벤트를
`Viewer("youtube", authorDetails.channelId)`와 `ChatInput`으로 변환합니다.
표시 이름 대신 채널 ID를 사용하고 메시지 ID는 API의 `id`를 유지합니다.
이벤트의 채팅 ID와 작성자 ID도 설정·조회 결과와 대조합니다.
대기열 크기·유효시간·직렬 LLM/음성/아바타 처리는 기존 `Application`을 재사용합니다.

소유자·관리자 표시가 있더라도 `/stop`, `/quit`, `/forget`은 **채팅 데이터**입니다.
어댑터에는 중지·종료·기록 삭제 기능을 전달하지 않습니다. 로컬 콘솔만 운영자 명령을 처리합니다.
Super Chat·스티커·멤버십·삭제·차단 이벤트는 답변 입력으로 처리하지 않습니다.
채팅 쓰기·메시지 삭제·방송 시작 기능은 없습니다.

## 수신 및 실패 정책

공식 [메시지 리소스](https://developers.google.com/youtube/v3/live/docs/liveChatMessages)와
[list API](https://developers.google.com/youtube/v3/live/docs/liveChatMessages/list)를 사용합니다.
첫 버전은 기존 `httpx`로 REST 조회를 수행합니다. 공식 문서는 효율적인 수신을 위해
`streamList`를 권장합니다. readiness에는 선택적 gRPC 전송을 추가했으며
[스트리밍·실제 수신 검증](youtube-stream.md)에 고정 프로토콜과 복구 정책을 기록했습니다.

- 최초 응답은 과거 채팅 기준점으로만 사용하고 발화하지 않습니다.
- 이후 `nextPageToken`을 유지하고 `pollingIntervalMillis` 이상 대기합니다.
- 통신 오류·5xx는 같은 조회 위치에서 실행 1회에 총 3회 추가 시도합니다. 중간 성공으로 한도를 초기화하지 않습니다.
  대기는 서버 조회 간격과 지수 지연 중 긴 쪽이며 초 단위 `Retry-After`도 존중합니다.
- 429·권한·할당량 오류는 중단합니다. 400은 설정·커서 확인 후 명시적인 재기준 설정을 요구합니다.
- 첫 응답 이후에 도착한 초기 이력도 실행 시작 시각보다 오래된 게시 메시지이면 제외합니다.
- 인증·권한·할당량 등 그 외 오류와 잘못된 응답은 수신을 중단합니다.
  자동 재인증이나 처음부터의 재조회는 하지 않습니다. 로컬 대화·음성은 계속 사용할 수 있습니다.
- 게시 시각이 기존 대기열 유효시간보다 오래된 메시지는 제외합니다.
  미래 시각은 30초까지만 허용하므로 운영 PC 시계를 맞춰야 합니다.
- 최근 4096개 메시지 ID를 메모리에 보관하여 재수신을 억제합니다.
  거절·대기열 넘침으로 빠진 메시지도 재제출하지 않습니다.
  영구적인 exactly-once 처리는 아니며 캐시 밖의 ID나 프로세스 재시작을 넘는 중복 제거는 보장하지 않습니다.
- 정상 종료·취소 시 수신 작업을 취소하고 HTTP 연결을 닫습니다.
  서버 오류 본문·토큰·채팅 내용은 오류 로그에 넣지 않습니다.

## 선행 검증 후 운영자가 준비할 설정

먼저 [OBS 로컬 녹화 절차](obs-local-recording.md)의 실제 모델·음성·중지·자막·중복 오디오
확인을 끝내고 결과를 기록합니다. 아래 설정은 그 후에 활성화합니다.

```yaml
youtube:
  enabled: false
  live_chat_id: ""
```

`live_chat_id`는 동영상 ID나 채널 ID가 아닙니다. 운영자가 해당 방송의 실제 채팅 ID를 지정합니다.
인증된 계정의 OAuth 액세스 토큰은 실행 프로세스 환경변수 `YOUTUBE_ACCESS_TOKEN`으로 전달합니다.
토큰을 YAML·명령 인자·커밋·테스트 기록에 넣지 마세요.
이 수동 방식은 `auth_mode: manual`에서 유지되며 만료 시 운영자가 교체 후 재시작합니다.
readiness의 신규 `auth_mode: oauth`는 [YouTube 인증](youtube-auth.md)의 명시적 승인·OS 저장·자동 갱신과
방송 ID로 채팅 ID를 조회하는 경로를 사용합니다. 두 모드 사이의 자동 대체는 없습니다.

기본 비활성화에서는 어댑터를 생성하거나 인증 정보를 읽거나 연결하지 않습니다.
`--once`도 방송 채팅을 연결하지 않습니다.
선행 검증과 인증 준비 후에만 로컬 설정을 `enabled: true`로 바꾸고 기존 명령을 실행합니다.

```powershell
uv run --locked python -m virtual_ai --config configs/app.yaml --backend koboldcpp
```

로컬 `/stop`은 현재 응답과 대기열을 비웁니다. **채팅 수신 자체를 일시 정지하지 않으므로**
이후 새 메시지는 다시 처리될 수 있습니다. 완전히 종료하려면 로컬 `/quit`을 사용합니다.
기존 KoboldCpp 중단 정리 실패 시 다음 생성이 차단되는 보호 동작은 그대로 유지됩니다.

## 검증 기록 (2026-09-22)

기준 브랜치 `feat/obs-subtitles`, 기준 커밋 `c2d1ca5` 위의 `feat/youtube-chat` 작업입니다.
가짜 전송 계층에서 변환·최초 과거 채팅 제외·중복·조회 위치 유지·재시도 한도·서버 대기 간격·
잘못된 응답·인증 오류·취소 시 연결 정리·비활성화·CLI 종료·운영자 명령 분리를 검사합니다.
Windows / Python 3.14.7에서 채팅 테스트 22개, 전체 **377 passed**를 확인했습니다.
`uv sync --locked`, `ruff check .`, `ruff format --check .`도 통과했습니다.

실제 OBS 녹화 / YouTube 인증·수신 / 네트워크 단절 후 실제 재접속 /
채팅→음성·표정·입·자막→녹화는 **미검증**입니다. 치지직은 **미구현**입니다.
실제 검증 시 커밋 SHA, 실행 환경, 사용 API, 관측 시간, 중복·누락·지연,
중지·종료 결과를 기록하고 토큰이나 실제 시청자 메시지는 커밋하지 않습니다.
