# 방송 채팅 선택·공정성·과부하

2026-09-23 readiness 미커밋 구현. 규칙 기반 자동 검증 완료. 실제 방송은 준비 대기 상태다.
모든 채팅에 답하는 것을 목표로 하지 않는다. `Application`은 REST·gRPC·콘솔 일반 입력에 같은
`SelectionPolicy`를 적용하고 기존 `ChatInput`/`submit()` 경로를 유지한다.

## 기본 규칙

```yaml
limits:
  queue_size: 20
  queue_ttl_seconds: 30
  queue_per_user: 2
  queue_max_consecutive: 1
```

- 사용자 키는 `(platform, user_id)`다. 사용자가 이미 2건을 기다리고 있으면 새 요청을 거절한다.
  현재 생성·재생 중인 응답은 대기 건수에서 제외한다.
- 기다리는 순서대로 선택하되, 한 번 선택된 사용자의 남은 메시지는 다른 대기 사용자 뒤로 옮긴다.
  예: A1·A2·B1·B2·C1 → A1·B1·C1·A2·B2. 메시지를 옮겨도 원래 만료 시각은 바뀌지 않는다.
- 연속 선택 상한은 다른 사용자가 기다릴 때 적용한다. 혼자 채팅하는 사용자를 영구 차단하지 않는다.
  이 제한은 실제 발화 성공 횟수가 아닌 응답 시도 선택 횟수에 적용되므로, 생성 오류로 특혜를 얻지 않는다.
- 전체 20건이 찼으면 **새 입력을 거절**한다. 기존 대기자를 계속 밀어내는 과부하 동작을 피한다.
  정책을 주입하지 않은 독립 `InputQueue` 호출은 이전 FIFO·최고령 제거 동작을 유지한다.
- 같은 사용자의 같은 내용을 TTL 동안 제한된 캐시로 제외한다. NFKC·대소문자·공백·보이지 않는 형식 문자를
  정규화한 SHA-256을 사용하며 ID를 바꾸어 보내도 걸러진다. 다른 사용자의 같은 질문은 독립 요청으로 취급한다.
  의미가 비슷한 바꿔 쓰기나 여러 계정의 동일인 판별을 하는 AI 검사는 아니다.
- 메시지 ID 중복 캐시와 내용 해시 캐시는 각각 `queue_size × 2`건이다. TTL/상한으로 제거되며
  영구 중복 제거 또는 exactly-once를 보장하지 않는다. `/stop`은 대기열과 선택 순서를 비우지만
  반복 억제 캐시는 TTL 동안 유지한다.

오래된 메시지는 `put`·`pop`·대기열 길이 조회에서 제거한다. YouTube 게시 시각도 `ChatInput.published_at`에
전달하여 **게시부터 대기까지 합친 나이**가 TTL을 넘으면 제외한다. 예를 들어 네트워크에서 25초 지연된
입력은 TTL 30초를 다시 얻지 않고 남은 5초만 기다린다. 수신 때 남은 시간을 monotonic 만료 시각으로 바꾸며,
미래 게시 시각도 대기 TTL을 늘리지 못한다. 로컬 입력은 게시 시각이 없어 접수부터 TTL을 적용한다.
이미 선택되어 생성 중인 응답을 TTL로 중간 취소하는 정책은 아니다. 즉시 중단은 운영 명령을 사용한다.

## 신뢰 경계·집계·메모리

관리자 문구·플랫폼 관리자 표시·`Viewer`의 이름으로 우선순위를 올리지 않는다. 일반 콘솔 문장도 같은
선택 규칙을 따른다. `/stop`, `/panic` 등은 기존 신뢰된 로컬 콘솔에서 직접 실행하며 대기열을 기다리지 않는다.
시청자가 보낸 같은 문자열은 대화 데이터다.

`/status`의 `input_drops`는 `duplicate`, `repeated_content`, `user_limit`, `overflow`, `expired`,
`cleared`, `invalid_input`, `input_locked`를 프로세스 누적으로 집계한다. 사용자별 통계를 만들거나
실제 사용자 ID·원문·내용 해시를 일반 로그에 남기지 않는다. 기존 응답 UUID 기반 폐기 이벤트는 유지한다.
이 집계는 앱/대기열에 도달한 입력에 관한 것이며 전송 어댑터가 앞서 제외한 이벤트까지 센 것은 아니다.

대기 항목·만료 정보·응답 접수 기록은 전체 상한 이내이며 캐시도 고정 상한을 갖는다. 선택 정책은 직전 사용자와
제한된 연속 횟수만 저장한다. 입력 본문은 설정 최대 4000자, 사용자/메시지 ID는 각 256자, 플랫폼은 32자 이내로
제한한다. 신규 의존성·사용자별 영구 상태·AI 점수 계산은 없다.

## 검증

`test_chat_selection.py`와 `test_input_overload.py`의 33개 검사에서 사용자별 상한, 순환 선택, 기다린 사용자 보호,
정규화 반복 제외, 설정 검증, 게시 시각 기준 만료, 순서 변경 후 만료, 비밀 없는 집계를 확인했다.
5만 건의 새 사용자 입력으로 대기열·캐시·만료 정보 상한을 확인했고, 연속 스팸 중 다른 대기자 선택과
앱 5000건 입력 시 접수 기록 상한·만료 후 미발화를 검사했다. 이는 가짜 입력 검사이며 실제 방송 성능 실측은 아니다.
전체 547개와 하위 검사 9개, Ruff lint/format·mock 실행·diff 공백 검사도 통과했다.

예를 들어 응답당 LLM 2초+TTS 2초+재생 4초+정리 1초라면 직렬 처리량은 `60 / 9 ≈ 6.7건/분`이다.
이는 설명용 가정이다. 실제 처리량·이탈률·대기 시간은 고정된 실제 환경에서 별도로 측정한다.
실제 YouTube 승인·방송 수신·청취·OBS 검증은 기존 대기 상태를 유지한다.
